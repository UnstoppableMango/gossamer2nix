# Dependency Management Bridge: `pip2nix`

This document was compiled by reading the [`nix-community/pip2nix`](https://github.com/nix-community/pip2nix) repository directly — `README.rst`, `CHANGELOG.rst`, `setup.py`, `pip2nix.ini`, `pip2nix/{cli,generate,confspec.ini,default.nix.j2}`, `pip2nix/models/{package,egg_writer}.py`, `default.nix`, `flake.nix`, and a generated sample `python-packages.nix` at the repo root — via GitHub's raw-content and REST APIs on **2026-07-26**, `master` branch (HEAD at commit `948d568`, 2025-07-16).
It exists as prior-art survey for `gossamer2nix`'s own deps-lock/Nix adapter (see [GOALS.md](../../GOALS.md)); see [DEPS.md](../DEPS.md) for the equivalent read of Gossamer's own dependency model, whose structure this document mirrors.

**This reflects one point-in-time reading of upstream `master` and may drift. Re-verify against current upstream source before depending on exact details.**

**Key finding, up front: `pip2nix` is not a lockfile translator — because pip's native `requirements.txt` format has no such lockfile to translate, `pip2nix` embeds a large chunk of pip's own internal resolver machinery (imported directly from `pip._internal`) and drives it against the live network at generation time, using `nix-prefetch-url`/`nix-prefetch-git`/`nix-prefetch-hg` to compute Nix fixed-output-derivation hashes as a side effect of that resolution.** There is no separate "lock" step and no offline/sandboxed generation mode. This is the single biggest structural difference from `poetry2nix`/`gomod2nix`-style tools that instead translate an already-resolved, already-hashed lockfile. See §4 and §8.

## 1. What `pip2nix` is, and its history

`pip2nix` "generates Nix expressions for Python packages," aimed at Python developers using Nix to manage dev environments (`README.rst`). Per its own README, it was created because the author "needed something that can work not only with pypi but also with local paths, VCS links, and dependency links" — i.e. it targets the full generality of what pip itself can install, not just PyPI.

Project timeline (`README.rst`, `CHANGELOG.rst`):
- Started 2015 by Tomasz Kontusz.
- Maintained by Johannes/Martin Bornhold from 2016.
- Forked and taken over by Asko Soukka in 2019, moved to the `nix-community` GitHub org, current listed maintainer (`maintainer=@datakurre` in the repo description).
- Latest released/dev version in `setup.py` at the read commit: `0.9.0.dev1`. The sample `python-packages.nix` checked into the repo root was generated by `0.8.0.dev1`.

Explicitly stated in the README: **"pip2nix is not yet mature software."** That line has apparently stood through the whole life of the project (it appears in the current README as of this reading, over a decade after the project's creation).

The README also draws its own contrast against the other well-known Python-freezer, `pypi2nix` (a *different, now-abandoned* project — GitHub description literally reads "Abandoned! Generate Nix expressions for Python packages"): "`pip2nix` can be used to extend nixpkgs' Python package set and reuse its package functions, where `pypi2nix` maintains [a] separate package tree from nixpkgs." I.e. `pip2nix`'s output is designed to be layered as an overlay on top of nixpkgs' existing `pythonPackages` (via `super.buildPythonPackage`, see §6), not a self-contained package universe.

| Stars / forks | 242 / 32 |

So: **not archived, not formally deprecated, still receives occasional maintenance and dependency-bump PRs — but activity is low and reactive, not a healthy release cadence.** Concretely:
- Recent open issues are substantive, unaddressed compatibility problems: `#105` (`ImportError: libstdc++.so.6` during generation, 2026-01-30), `#99` ("Fix issues running on macOS", 2025-05-29), `#97` ("`git+url` dependencies won't work (?)", 2024-09-12) — all still open with zero or one comment.
- `flake.nix` pins `nixpkgs` to `ref = "nixos-20.09"` (a 2020 release) rather than tracking current nixpkgs, and `default.nix` uses `pythonPackages ? "python39Packages"` as its default — both signs the project's own dev/build environment is stale relative to current nixpkgs, even though the *tool* nominally still runs against newer targets when invoked by hand.
- `pip2nix/generate.py` (the resolution driver, §4) is a thicket of `try/except TypeError`/`ImportError` fallback chains reaching across at least four different historical shapes of pip's internal `Resolver`/`RequirementPreparer`/`RequirementSet` constructors (pip 9-ish through pip ~21+). This is direct evidence that pip's internal, explicitly-unstable API has repeatedly broken `pip2nix`, and the fix pattern has been "add another `except` branch" rather than a rewrite — a maintenance-burden smell, not a design flaw per se, but telling about the tool's trajectory.
- Issue `#62` ("Incompatible with nixpkgs-unstable: unexpected argument 'self'") shows this exact breakage pattern recurring against nixpkgs' Python infra too, and was eventually closed/fixed — but it illustrates the tool sits at the intersection of two independently-shifting unstable APIs (pip internals *and* nixpkgs' Python package set), which is a structurally fragile place to live.

**For comparison, `poetry2nix`** (the more commonly recommended `*2nix` tool for Python today) is in a similar-but-better state: not archived (`archived: false`, pushed as recently as 2026-07-27), but its original maintainer stepped down in November 2024 citing that they'd moved off Poetry, the repo has 187 open issues, and the maintainer's own stated recommendation going forward is `uv` + `uv2nix` (still experimental as of that recommendation). `pip2nix` was never the "recommended" tool even at its healthiest — it's a longtail option for projects still on plain pip.

**Bottom line for `gossamer2nix`: `pip2nix` is a useful architecture reference (§4, §6, §8) but a cautionary tale operationally.** A tool whose entire hashing/fetching pipeline is built by re-implementing/importing another tool's *internal, unversioned* API surface (pip's) is fragile in a way that's largely avoidable if Gossamer's own resolver/lockfile (per `DEPS.md` §6-7) is stable and public, which is a strong argument for `gossamer2nix` consuming Gossamer's own `project.lock` directly (as `gomod2nix`/`poetry2nix` do with their respective ecosystem-native lockfiles) rather than re-deriving a resolution.

## 3. Input

**What `pip2nix generate` consumes:** a `requirements.txt`-style file (or files, via repeated `-r`), passed either on the CLI (`pip2nix generate -r requirements.txt`) or declared in a `pip2nix.ini`/`pip2nix.cfg` config file's `requirements` key (`pip2nix/confspec.ini`; `requirements = requirements_list()`, mandatory, no default). Also accepted, mirroring pip's own CLI surface (`pip2nix/cli.py`, built on `click`, wrapping `pip`'s `InstallCommand` — `pip2nix/generate.py`):
- `-c`/`--constraint` constraint files (`options.constraints`).
- `-e`/`--editable` local/VCS editable specifiers.
- `--no-index`, `--index-url`, `--extra-index-url` for registry selection.
- `--no-binary` (pip2nix forces wheel-vs-sdist choices itself; see §4).

**Critically, this input format has no native lock/hash guarantee.** A plain `requirements.txt` line like `requests==2.32.4` (the literal content of `examples/shell/requirements.txt` in the repo) pins a *version string* but not a content hash, and it says nothing about the full transitive dependency graph — that's pip's job to work out at install time, normally freshly, against whatever index state exists *right now*. Unlike `pip-compile`'s `--generate-hashes` output or a Poetry `poetry.lock`, there's no expectation that a bare `requirements.txt` is itself reproducible. `pip2nix` does not require a hash-pinned/frozen input — it accepts exactly the loose, ecosystem-native `requirements.txt` format and does all resolution and hashing itself (§4), which is both its whole reason to exist and the source of most of its fragility.

## 4. Resolution mechanism: reusing pip's own (legacy) resolver, live

This is the part most worth studying for `gossamer2nix`'s own design, because it's the opposite end of the spectrum from Gossamer's own greedy-descending, in-process resolver (`DEPS.md` §6).

`pip2nix/generate.py` defines `NixFreezeCommand`, a subclass of pip's own `pip._internal.commands.install.InstallCommand`. Rather than reimplementing dependency resolution, `pip2nix` **is** (a thin shell around) `pip install`, with installation itself suppressed:

```python
options.no_install = True   # Download only
options.upgrade = True      # Download all packages
options.use_wheel = False   # We'll build the wheels ourself
```

`super_run()` reconstructs pip's actual internal install pipeline by hand: builds a `PackageFinder` against the configured index URL(s), constructs a `RequirementSet`, a `RequirementPreparer`, and pip's own `Resolver` (imported as `pip._internal.resolve.Resolver`, or `legacy_resolve.Resolver`, or `resolution.legacy.resolver.Resolver` depending on which pip is installed — the import itself is wrapped in a cascading `try/except ImportError`), then calls `resolver.resolve(requirement_set)` — i.e. it invokes **pip's real dependency resolver**, unmodified, so that `pip2nix`'s output is guaranteed to match what `pip install -r requirements.txt` would actually have installed on that machine at that moment.

Consequences of this design:
- **Network access is required at generation time**, unsandboxed — the finder hits the configured PyPI/index URL(s), and the resolver downloads/builds sdists and wheels to read their metadata (`setup_requires`/`tests_require`/dependency declarations), exactly as `pip install` would.
- **Resolution is not deterministic across time** in the way a committed lockfile is: re-running `pip2nix generate` against the same `requirements.txt` at a later date can produce a different `python-packages.nix` if the index has new releases, because there is no separate "resolve once, freeze it" step distinct from "generate the Nix expression" — they are the same act. The generated `python-packages.nix` *becomes* pip2nix's de facto lockfile after the fact (§6), but nothing enforces re-generation staying stable.
- `process_requirements()` additionally walks each resolved package's declared `setup_requires`/`tests_require` and any pip-discovered indirect dependencies (`resolver._discovered_dependencies`), re-invoking `resolver.resolve(...)` in a loop until no new requirements appear, to fully close the transitive graph (excluding `setuptools`/`wheel` themselves, popped explicitly since nixpkgs already provides these).
- `only_direct` config option, if set, skips all of the above and only freezes directly-requested (non-transitive) requirements.

This means `pip2nix`, uniquely among the `*2nix` family surveyed here, doesn't need to implement dependency resolution logic at all — it borrows it wholesale from the ecosystem's real package manager, at the cost of depending on that package manager's *internal, explicitly unversioned* Python API (see the `try/except` fallback chains throughout `generate.py`, and §2).

## 5. Fetching and hashing: `nix-prefetch-*`, live, trust-on-first-use

Once pip's resolver has determined the final package set and each package's concrete download link (a pip `Link` object — from PyPI, a VCS ref, or a direct URL), `pip2nix/models/package.py`'s `link_to_nix()` converts each into a Nix fetcher call, **computing the required Nix hash by shelling out to Nix's own prefetch tools at generation time**:

```python
def link_to_nix(link, cache={}):
    if link.scheme == 'file':
        return './' + os.path.relpath(link.path)
    elif link.scheme in ('http', 'https'):
        ...
        hash = prefetch_url(link.url_without_fragment)   # -> ['nix-prefetch-url', url]
        return 'fetchurl { url = "..."; sha256 = "<hash>"; }'
    elif link.scheme.startswith('git+'):
        ...
        hash, revision = prefetch_git(url, branch)        # -> ['nix-prefetch-git', ...rev_args, url]
        return 'fetchgit { url = "..."; rev = "<rev>"; sha256 = "<hash>"; }'
    elif link.scheme.startswith('hg+'):
        ...
        hash, revision = prefetch_hg(url, branch)          # -> ['nix-prefetch-hg', url, rev]
        return 'fetchhg { url = "..."; rev = "<rev>"; sha256 = "<hash>"; }'
```

So: **yes, this is exactly a trust-on-first-use model**, and it is explicit and unavoidable given the input format (§3) has no hashes to start from. `pip2nix generate` must have live, unsandboxed network + `nix-prefetch-url`/`nix-prefetch-git`/`nix-prefetch-hg` on `PATH` (the repo's own `pip2nix.ini` even wires `nix-prefetch-scripts` onto the wrapped binary's `PATH` via `makeWrapperArgs` for exactly this reason) to produce a `python-packages.nix`. Nothing about this step runs inside — or could run inside — a Nix build sandbox; it is entirely a pre-build, developer-machine (or CI-with-network) generation step, after which the *output* file is what gets consumed by a real sandboxed Nix build (§6).

One caching optimization exists: before regenerating, `NixFreezeCommand.process_requirements()` reads the *previous* `python-packages.nix` output file (if present) and regex-extracts existing `url = "..."; sha256 = "..."` pairs into an in-memory `cache` dict (`generate.py`), so previously-fetched packages whose URL is unchanged skip re-prefetching. This is a purely local, best-effort memoization of past hash computations — not a checked-in, shareable lockfile in its own right, and it's keyed on plain regex-matching the previous output text, not any structured format.

Local/`file://` links and same-directory `path` dependencies are passed through as a relative path expression with no fetch or hash at all (`return './' + os.path.relpath(link.path)`), analogous to Gossamer's unhashed `path` dependency kind (`DEPS.md` §3, §7).

## 6. Output: `python-packages.nix`, a nixpkgs-shaped overlay

The generated artifact (`pip2nix/generate.py`'s `process_requirements`, confirmed against the sample `python-packages.nix` checked into the repo root) is a single Nix file, an **overlay function** over nixpkgs' Python package set:

```nix
# Generated by pip2nix 0.8.0.dev1
# See https://github.com/nix-community/pip2nix

{ pkgs, fetchurl, fetchgit, fetchhg }:

self: super: {
  "click" = super.buildPythonPackage rec {
    pname = "click";
    version = "7.1.2";
    src = fetchurl {
      url = "https://files.pythonhosted.org/packages/.../click-7.1.2.tar.gz";
      sha256 = "06kbzd6sjfkqan3miwj9wqyddfxc2b6hi7p5s4dvqjb3gif2bdfj";
    };
    format = "setuptools";
    doCheck = false;
    buildInputs = [];
    checkInputs = [];
    nativeBuildInputs = [];
    propagatedBuildInputs = [];
    meta = {
      license = [ pkgs.lib.licenses.bsd3 pkgs.lib.licenses.bsdOriginal ];
    };
  };
  "MarkupSafe" = ...;
  "jinja2" = super.buildPythonPackage rec { ... propagatedBuildInputs = [ self.MarkupSafe ]; ... };
  ...
}
```

Key mechanics:
- **Per-package derivations via `super.buildPythonPackage`** (confirmed): each entry is literally a call into nixpkgs' own `buildPythonPackage` builder function, not a custom `pip2nix`-authored builder — this is the concrete meaning of the README's claim that `pip2nix` "extend[s] nixpkgs Python package set and reuse[s] its package functions."
- **`self`/`super` fixed-point overlay pattern**: intra-graph dependencies resolve via `self.<pkg>` (e.g. `jinja2`'s `propagatedBuildInputs = [ self.MarkupSafe ]`), letting downstream consumers override any individual package by layering another `self: super: {...}` overlay on top, standard nixpkgs overlay idiom.
- **`format` field** (`"setuptools"` vs presumably `"wheel"`/`"pyproject"` for other packages) tells `buildPythonPackage` which nixpkgs build path to use, set per-package by `pip2nix` based on what pip actually resolved/built for that package.
- **License mapping**: `pip2nix/models/package.py` maintains a hardcoded string→nixpkgs-license-attr table (e.g. `'Apache 2.0': 'asl20'`) plus dynamic lookups against nixpkgs' own `lib.licenses`, parsed out of each package's `PKG-INFO` (`License:` field and `License ::` classifiers). Emitted only when the `licenses` config flag is enabled.
- **Scaffolding**: `pip2nix scaffold <name>` (via Jinja2 templates `default.nix.j2`/`python-packages-overrides.nix.j2`) generates a project's `default.nix`, which `import`s the generated `python-packages.nix` overlay, layers a project-local `python-packages-overrides.nix` on top (for hand-written overrides `pip2nix` can't infer — native deps, patches, etc.), and fixed-points the whole stack via `pkgs.lib.fix`/`extends` against the base `pythonPackages` set (`default.nix` at repo root is exactly this pattern, self-hosted for `pip2nix`'s own packaging).

There is no separate machine-consumable "lockfile" distinct from this `.nix` file — `python-packages.nix` **is** simultaneously the Nix build recipe *and* the closest thing to a lockfile `pip2nix` produces (its only record of exactly which version+hash was resolved), consistent with the trust-on-first-use/no-separate-lock-step design noted in §4-5.

## 7. CLI and configuration reference

| Command | Purpose |
|---|---|
| `pip2nix generate -r requirements.txt [-c constraints.txt] [-e pkg] [--no-index] [--index-url URL] [--output FILE] [--configuration pip2nix.ini]` | Resolve (§4), fetch+hash (§5), and write the overlay (§6). Config file default-discovered as `pip2nix.ini`/`pip2nix.cfg` if `--configuration` omitted. |
| `pip2nix scaffold NAME` | Emit a starter `default.nix` + `python-packages-overrides.nix` for a new project via Jinja2 templates. |

`pip2nix.ini` config schema (`pip2nix/confspec.ini`, a `configobj` validate-spec):

```ini
[pip2nix]
requirements = requirements_list()                          # required, no default
constraints = string_list(default=list())
output = string(default="./python-packages.nix")
no_index = boolean(default=False)
only_direct = boolean(default=False)
index_url = string(default="https://pypi.python.org/simple")
extra_index_url = string_list(default=list())

[[package]]
[[[__many__]]]
additional_requirements = requirements_list(default=[])
excluded_requirements = requirements_list(default=[])
[[[args]]]
```

The `[[package]].[[[__many__]]]` block lets a project hand-patch individual packages' requirement sets (add/exclude specific transitive deps) directly in config, a manual escape hatch for cases where pip's resolution doesn't match what's actually needed under Nix.

`PIP2NIX_PYTHON_EXECUTABLE` env var overrides which Python interpreter `pip2nix` itself runs under (used by the self-hosted `default.nix` wrapper, §6, to pin `pip2nix` to a specific nixpkgs Python + `pip`).

## 8. The gap: what `pip2nix` has to do that `poetry2nix` doesn't

This is the direct answer to "why does this tool exist" and the clearest contrast for `gossamer2nix`'s own design.

| | Poetry (`poetry.lock`) | plain pip (`requirements.txt`) |
|---|---|---|
| Full resolved transitive graph committed to VCS | Yes | No (only what's written by hand, or by an external tool like `pip-compile`) |
| Per-package content hashes committed to VCS | Yes (multiple hashes per package, all published artifacts) | No (unless `pip-compile --generate-hashes` or `pip freeze --require-hashes` was used upstream, which `pip2nix` does not require or assume) |
| Deterministic across re-resolution | Yes — `poetry.lock` *is* the frozen resolution | No — a bare `requirements.txt` is just constraints; resolving it can yield different results run to run as the index changes |
| What the `*2nix` tool must do | **Translate**: parse an already-resolved, already-hashed lock format into Nix `fetchurl`/`fetchFromPyPI` calls. No resolution, no network-dependent hash computation needed at translate time (hashes are already present in the lock). | **Resolve, fetch, and hash, from scratch, live.** `pip2nix` has no lock format handed to it, so `generate.py` reimplements the "resolve" step by directly invoking pip's own internal resolver (§4), and the "hash" step by shelling out to `nix-prefetch-*` against the network (§5), because nothing upstream ever computed those hashes. |

So the entire raison d'être of `pip2nix`, and the entire reason it's structurally more fragile than `poetry2nix`, is that **pip's native input format is a constraint list, not a lockfile** — `pip2nix` has to manufacture the equivalent of a lockfile itself, on every generation run, by actually running (a piece of) the real package manager against the live network, rather than mechanically translating a static file. `poetry2nix` (and, per `DEPS.md` §6-7, a `gossamer2nix` built against Gossamer's own `project.lock`) gets to skip that whole problem for free because the ecosystem-native tool already did the resolution-and-hashing work and published the result as a stable, checked-in artifact.

## Input / Output summary

**Input** (ecosystem-native, consumed by `pip2nix generate`):
- One or more `requirements.txt`-style files (plain pip constraint syntax: name, optional version specifier, optional VCS/URL/local-path source, optional environment markers/extras). **No hashes required or expected.**
- Optional `-c` constraint files, `-e` editable specs, index URL configuration.
- Optional `pip2nix.ini` for output path, per-package requirement overrides, and index settings.
- Implicitly, and unavoidably: **live network access to the configured PyPI/index**, since resolution (§4) and hashing (§5) both require it. There is no offline/frozen-input generation mode.

**Output** (Nix-consumable, written by `pip2nix generate`):
- A single generated `<output>.nix` file (default `python-packages.nix`): a `{ pkgs, fetchurl, fetchgit, fetchhg }: self: super: { ... }` overlay, one `super.buildPythonPackage` (or wheel-format equivalent) attribute per resolved package, each with a `src = fetchurl/fetchgit/fetchhg { url = ...; sha256 = ...; }` computed via `nix-prefetch-*` at generation time, intra-graph deps wired through `self.<pkg>`, and best-effort `meta.license` mapped from PyPI classifiers to nixpkgs license attrs.
- This file doubles as the project's de facto lockfile (§6) — there is no separate lock artifact.
- Optionally, `pip2nix scaffold` also emits a starter `default.nix` (fixed-point `extends` of the generated overlay + a hand-written local-overrides overlay + nixpkgs' base `pythonPackages`) and `python-packages-overrides.nix`.
